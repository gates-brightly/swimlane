swim — operator-in-the-loop automation

  An AI session (the planner) and its subagents (workers) write operational
  work as bash lane scripts. A human operator runs them with `swim run`, in
  environments the session can't reach (VPN-only accounts, their own
  credentials). Every step and result lands in a log the session reads back
  to decide the next step.

    The session writes. The operator runs. The log reports.

  The planner never executes against the target itself.

USAGE
  swim <command> [flags] [args]
  swim N|JOB [N|JOB ...]       shorthand for `swim run N|JOB ...`, e.g. `swim 1 2`
  swim <command> --help        detail for one command
  swim --help                  this guide (written for AI planners/workers)

  help [command]           this guide, or one command's detail

CONCEPTS
  lane        A numbered slot, swim 1..99. One script (lane.N.sh,
              or lane.N.py, lane.N.ts, a binary lane.N, ...: see OTHER LANGUAGES),
              one log (.swim/logs/agentN.log), owned by one worker at a time. Lanes are
              always numbers; there are no named lanes. A repo has no lane
              count: its lanes are the ones in use (a script that isn't a
              stub, a current log, or a running lane). swim new N starts
              one; swim archive N (with a stub or no script) drops one.
  round       One lane script's contents: a single goal ("cut over service X",
              "diagnose Y"). Rewritten per round; disposable. A round that
              passed is "done": `swim all` won't run it again (`swim run N`
              or `swim all --rerun` will) until the lane gets a new round.
  run         One `swim run` / `swim all`. Each gets a run id (r-<utc>-<hex>, or
              --run-id ID), exported to every lane as $SWIM_RUN with the lanes
              in the run as $SWIM_RUN_LANES, and recorded in the log, status.yml
              and .swim.log. Use it to tell this run's outputs from leftovers.
              `swim log <run>` and `swim status --run <run>` show one run. A lane
              run directly with bash is a run of its own.
              On a terminal with more than one lane, the operator's live view is
              interactive: ← → pick a lane to read its log, ↑ ↓ scroll, Esc
              returns to all lanes, ? lists the keys (--no-tui or SWIM_TUI=0:
              off). It changes nothing a lane sees or records, except its
              approvals: y / n answer a lane that's asking, and on a selected
              lane that hasn't asked yet, y pre-approves its known guards
              (Guards: and guard calls), n pre-declines them (dry runs), u
              undoes. Marks show ✓ pre-approved, ✗ dry run or ? N guards. A
              pre-answer is the operator's prompt answer given early: FLAG=1/0
              and signed approvals still come first, it comes before -y, it's
              pinned to the lane's script (a changed script asks again), and
              it lasts this run only. The log says "pre-approved by <user> at
              <time> in the live view"; the chain records method preapproved;
              unused pre-answers are listed after the summary.
  job         One round's unique id, written in the script header as
              `# Job: <id>` by `swim new` (a UUID, or your own with --job).
              It is recorded in the log, status.yml, the live view and the
              summary, and exported to steps as $SWIM_JOB (tag resources with
              it so gates can tell "ours" from "theirs"). Pin a command to a
              job by passing the id instead of a lane number: `swim run 3f2a9c1e`
              runs exactly that job, and refuses if no lane holds it any more
              (the script was rewritten or stubbed). A script without a Job:
              line gets an id when it starts, so it can't be pinned before then.
  step        One command run through `swim step` (via run/gate/snapshot),
              recorded with a header, its output and exit code.
  gate        A step whose failure stops the round before any later step.
  guard flag  An env var that approves one destructive action up front, e.g.
              FIN_ALLOW_DELETE_ZG_ITEMS=1. Unset, swim asks the operator at the
              terminal ("requires human approval of task: ... Y/N [N]"); with
              no one to ask (CI, no terminal) or a "no", the step dry-runs.
  lock        A named resource a round needs exclusively (# Locks:). A lane takes
              all its locks at once, after its dependencies pass and before it
              starts; lanes waiting for one show "locked (name: swim N)". Locks
              hold within a run and across concurrent swim runs in the repo
              (files under .swim/locks/, released when the lane's process ends,
              even if killed). They don't protect across machines, and a lane
              run directly with bash takes none. Use After: for order; Locks:
              when either order is fine but overlap isn't.
  dependency  "swim B starts after swim A succeeds". Declare it in B's script
              header, `# After: A` (lane numbers or job ids), or for ordering
              that holds every round, in config `deps`. If A fails or is
              skipped, B is skipped.
  always lane Standing setup, like a CI before_script (# Always: yes): lint,
              fmt, init. It never counts as passed, so `swim all` runs it
              every time, first, and every other lane in the run waits for it
              to finish; only lanes that name it in After: need it to pass.
              `swim run N` pulls in the Always lanes N names, no others. With
              # Rerun-Children: yes, `swim all` reruns every lane downstream
              of it, even ones that passed. It isn't a round: never assign,
              rewrite, archive or stub one (swim refuses without --force).
  job         Part of a lane: any lane can be split into jobs, numbered
              under it and nested to any depth (1.1, 1.2, 1.5.9.9). The lane's
              header (Round:, After:, Locks:) comes first; each job starts at
              a "# swim job N.K" line, then its own header (Round:, Job:,
              Always:, Timeout:) and steps. Jobs with steps run in file order
              and the first failure skips the rest; each has its own log
              (swim log 1.2) and status. A job id names it and every job
              under it: `swim run 1.5` runs them all, `After: 1.5` waits for
              them all. Always: on a job covers those under it; other lanes
              wait only for the lane's Always jobs. swim adds the library
              load, lane_init and summary, and runs .swim/groups/lane.N.<job>.sh:
              edit the lane's file, never that. Code before the first job runs
              in every job, after lane_init.
              In Python, TypeScript or Go, mark jobs in comments (# or //) the
              same way: each job runs the whole program, and the SDK's jobs()
              calls its function (keys "1.2" or "2"; the closest wins).
  group file  A lane of jobs named lanes.<name>.sh at the repo root, for standing
              jobs worth committing (fmt, lint, test): it's the lane its jobs
              name. It can't also have a lane.N.sh; swim new/stub refuse it.
  stub        The placeholder a lane holds between rounds (`swim stub`).
  archive     A finished log renamed agentN.prev-<what>.log (`swim archive`).
              Logs are kept; rounds are not.

FILES (repo root)
  .swim.lock            the syntax versions this repo's lanes use; written on
                        the first run. Commit it. If swim refuses to run over a
                        version mismatch, follow its instructions (and see
                        `swim lock --help`); never edit or delete the lock to
                        get past it.
  .swim.log             project log: one line per top-level action (rounds
                        written, run, passed/failed, skipped, archived, stubbed,
                        notes). A new agent reads it first. Git-ignored by
                        default; remove it from the swim block in .gitignore
                        to commit the project's history.
  Also git-ignored by `swim init`:
  lane.N.sh              lane N's script (the current round); or lane.N.<ext> in
                         another language, or a compiled lane.N (exactly one per lane)
  lane.N.yml             optional metadata for lane N's script (round, job, after,
                         guards, locks, timeout, ...), over its header (OTHER LANGUAGES)
  .env.swim              lane-scoped env: [lane N] sections of KEY=VALUE (ENV FILES)
  .lane.N.rc             deprecated: operator-local env sourced by lane_init (ENV FILES)
  .swim/status.yml      last state of every lane (see READING RESULTS)
  .swim/logs/agentN.log         lane N's log, append-only, plain text (ANSI

  .swim/logs/agentN.prev-*.log  archived logs (`swim log N --all`)
  .swim/snapshots/      output saved by `snapshot` steps
  .swim/out/<job>/<run>/  a round's outputs ($SWIM_OUT; Outputs:), read-only once it ends
  .swim/chain.jsonl     chain of custody: hash-linked, signed approvals and rounds
  .swim/scripts/        every lane script a round ran, by SHA-256
  approvals/            signed approvals (committed): lane.N.<sha12>.signature for one
                        exact script, auto.USER.signature standing for USER's jobs
  lookup.yml            who's who: users' SSH keys, groups, approval rules (committed);
                        a rule with evidence: true counts only evidence-bound approvals
  .swim/evidence/       each round's evidence (evidence steps), and blobs by hash for diffs
  .swim/hub.yml         this directory's hub enrollment (swim hub enroll), private
  .swim/queue/          queued batches (swim queue): NNNN-<id>.queue waiting,
                        .running claimed by a worker, done/ consumed with results
  .swim/runs/RUN.yml    each run's record: when every lane was ready, queued,
                        locked, started and finished (`swim timeline`)
  .swim/laneN.pid       present while lane N runs
  ~/.config/swim/config.yml   configuration (outside the repo; see CONFIG)

PLANNER WORKFLOW
  0. Catch up. Read .swim.log (`swim log`, or `tail -50 .swim.log`), then
     `swim status`. Don't redo or contradict what it records without asking.
  1. Look before writing. Run `swim status`. Confirm with the operator which
     lanes are idle. Never write to a lane that is running or holds a pending
     round someone else may be about to run.
  2. Assign each worker one lane number. A worker writes only lane.N.sh.
     Use a lane `swim status` shows idle, or a number not in use (any of
     1..99: there's no lane count to raise). Never an Always lane
     (# Always: yes; `swim plan` marks it [*]): name it in After: if your
     round needs it to pass. Never edit the config yourself.
  3. Write the round: `swim new N "<goal>"`, then fill in the steps. Keep the
     header (Round:, Goal, Steps, Guard flags) accurate: the operator reads
     it without you.
  4. Run `swim lint N` and fix its errors (warnings deserve a look). Check
     the shape with `swim plan` (the dependency tree, predicted skips,
     guard flags) and fix anything unexpected. Then hand the operator the
     exact command, e.g. `swim run 1 3`, or pinned to
     the jobs you wrote, e.g. `swim run 3f2a9c1e 7b4d4e2a`, so a lane rewritten
     in the meantime is refused instead of run. Add any guard
     flags they must set to approve destructive steps, e.g.
     `FIN_ALLOW_DELETE_ZG_ITEMS=1 swim run 2`. Explain what each flag approves.
  5. After the run, read the log (`swim log N`, or `swim log <job>`) and
     .swim/status.yml. Validate real
     outcomes in the step output (resource ids, counts, plan says "No
     changes"); a PASS line only means exit 0. If the run was slow,
     `swim timeline` shows which lane held it up (the longest chain) and
     whether the time went to work, dependencies, slots or locks.
  6. Record the results (with the job id) where your project tracks them,
     then `swim archive N|JOB ... [--as <what-happened>]` and `swim stub N "<why idle>"`.
  7. Out-of-scope findings go on a follow-up list, never into the round.
     Record decisions and findings the next agent needs with
     `swim note "<text>"` (or `swim note --lane N "<text>"`). Keep notes
     factual and short; never put secrets in them.
  8. Declare ordering in the scripts you write: `# After: 1` in lane.2.sh
     makes swim 2 wait for swim 1 to pass. Write it in the header, never just
     in prose: swim only enforces what it can parse. Pin to a job id
     (`# After: 3f2a9c1e`) when the dependency must be that exact round.
     Ordering that holds for every round can live in config `deps:` (outside
     the repo); give the operator the exact YAML lines for that.
  9. Batches can wait their turn: while lanes are still busy, write the next
     rounds, then have the operator queue them with the approvals they give
     up front (`swim queue add 4 5 --approve FIN_ALLOW_DELETE_ZG_ITEMS`). A
     worker (`swim watch`) runs the batch as soon as swim is idle. Queue only
     what you'd hand over to run unattended: a queued batch never asks, so
     every guard it doesn't approve is a dry run.

WORKER RULES
  - Write only your own lane.N.sh. Never edit shared files (registries, plan
    docs, config, other lanes). Report the exact lines to the planner, who
    applies them.
  - Prefer new modules over changing shared ones while other lanes run. Any
    change to a shared module must leave existing users unchanged.
  - NEVER edit a lane script while it may be running. Bash reads scripts
    incrementally; a mid-run edit corrupts the run. `swim status` shows
    running lanes; `swim new`/`stub`/`archive` refuse to touch them.
  - Use names (resources, tags, snapshot labels, archive names) that no other
    session will reuse. $SWIM_JOB is unique per job; prefer it for tags.
  - Keep the `# Job:` line from `swim new`. Don't copy a job id into another
    script: ids must be unique, and pins rely on that.

WRITING A LANE SCRIPT
  Start from `swim new N "<goal>"`. The library functions:

  lane_init N                     claim lane N: cd to repo root, STEP_LOG=.swim/logs/agentN.log,
                                  source .lane.N.rc (deprecated), write the round header, mark running,
                                  export SWIM_JOB (the script's job id), SWIM_DEADLINE and
                                  SWIM_TIMEOUT (from Timeout:). Refuses if lane N is already
                                  running. Call it first.
  stage NAME                      start a stage: snapshot, check, change or verify. Steps
                                  before the first stage are setup. See STAGES below.
  run [opts] "<label>" cmd [args...]
                                  one step; records PASS/FAIL <label>. A failure does
                                  NOT stop the round (checks keep going).
  gate [opts] "<label>" cmd [args...]
                                  like run, but failure (after the last attempt)
                                  stops the round here (STOP).
  snapshot [opts] "<label>" cmd [args]
                                  read-only step whose output (the last attempt's)
                                  is also saved to .swim/snapshots/laneN-<time>-<label>.txt.
    opts, before the label:
      --timeout D                 stop the step after D (30s, 5m, 1h30m): FAIL
                                  (timeout: step limit D), exit 124. 0 turns off the
                                  script's Step-Timeout: for this step.
      --retry N                   try up to N more times on a non-zero exit (a step
                                  that timed out is retried too)
      --backoff D                 wait D before the first retry, doubling, capped at 5m,
                                  with +/-20% jitter (default 2s)
      --retry-on CODES            retry only on these exit codes, e.g. 1,255
      --no-retry-timeout          don't retry an attempt the step limit stopped
      --soft                      in a Fail: hard round, this step's failure doesn't end it
    The round's Timeout: always wins: no attempt runs past it, and a retry that
    couldn't start before it isn't attempted (the round stops, as for a timeout).
    TIME LIMITS: a step runs in its own process group, and a limit stops all of
    it: SIGTERM to the group, SIGKILL after 5s, so bash -c 'server & tests'
    leaves no server behind. What a step leaves running when it ends on its own
    is left alone. A step whose stdin is the terminal (a lone lane run from a
    terminal, or swim step by hand) stays in the lane's group so it can read
    the keyboard: a limit then stops only its own process, not its children.
    Each attempt is in the log; the step counts once (one PASS or FAIL). Only put
    --retry on read-only or idempotent steps, never on a change that isn't.
  guard FLAG "<action - date, reason>"
                                  true if FLAG=1, or (FLAG unset) the operator answers y
                                  to "swim N requires human approval of task: <action>
                                  Y/N [N]" (swim run asks, even for parallel lanes; in
                                  the interactive view Enter opens the waiting lane), or
                                  the run was started with -y; otherwise logs SKIP with the
                                  approval hint and returns false. FLAG set to anything
                                  else (FLAG=0) never asks. Write <action> for the person
                                  approving it: what it changes, and why. The question
                                  shows <action> and the evidence made safe: escape
                                  sequences, control characters (\r, backspace) and bidi
                                  overrides are removed, so a lane can't rewrite it.
  confirm "<question>" [answer]   operator must type the answer (default "yes");
                                  anything else, or no stdin, stops the round.
  last_failed                     true if the previous step failed.
  any_failed                      true if any step in this round failed.
  drift "<what differs>"          record DRIFT (deployed state differs from code).
  msg [--progress N/M] "<text>"   post the lane's status message: where a long job is
                                  now ("migrating billing", 7/25). It shows in the live
                                  view, swim status and the hub; the latest wins, msg ""
                                  clears it, and the round's end does. The log gets MSG
                                  lines, at most one per msg_log_interval (default 10s;
                                  changes only; the latest when a step or the round ends).
                                  A command inside a step can post too: swim msg "...".
                                  Never fails the round.
  stop "<reason>"                 record STOP and end the round now (in a handler: record
                                  it, and the handler carries on).
  evidence [opts] "<label>" cmd   a check stage step whose output shows what the change will
                                  do (terraform plan, a diff): saved, normalized (ANSI,
                                  line endings, trailing space) and hashed as the round's
                                  evidence. swim approve signs it with the script, and a
                                  guard counts that approval only while this run's evidence
                                  matches (else a WARN, a diff, and the prompt or a dry
                                  run). Print stable output. A failure stops the round.
  input N|JOB NAME                print the path of an output of a round this one depends on:
                                  lane N's round this run waited on (it must have passed),
                                  or job JOB's latest passed round, even from an earlier run.
                                  Only lanes and jobs in After: (or config deps). A small value
                                  prints the value itself. Use it as "$(input 2 stats.json)";
                                  inside bash -c, call swim input. What was read, and its hash,
                                  goes in the chain. A failure records FAIL.
  output KEY VALUE                record a small value (an id, a version) among the round's
                                  outputs; dependents read it with $(input N KEY).
  reached STAGE                   true if the round started STAGE or a later one; an
                                  on_failure usually starts with: reached change || return 0
  summary                         run the outcome handlers, print + log the summary, record
                                  final state. Exits non-zero if any step failed. Put it last.

  Header (the `# Key: value` lines at the top; one space at most after the
  #, since indented comment lines are prose). Empty or missing means the default:
      # swim: syntax 2                the syntax this script is written in (see SYNTAX)
      # Round:   <goal>               required; a script without it is not run
      # Job:     <id>                 written by swim new; keep it. Default: one is made
                                      when the round starts (then it can't be pinned)
      # After:   <lane|job> [...]     wait for these to pass first, e.g. "2 3". Default: none
      # Always:  yes                  standing setup: runs every time, before every other
                                      lane in the run (see "always lane"). Waits only on
                                      other Always lanes. Default: no
      # Rerun-Children: yes           (Always lanes) swim all reruns every lane downstream
                                      of this one, even ones that passed. Default: no
      # Owner:   <who wrote it>       Default: - (swim new fills in $USER)
      # Created: <YYYY-MM-DD>         Default: the file's modification date
      # Guards:  FLAG  <what it approves (date, reason)>
                                      one line per flag. Flags the body uses are found
                                      anyway; list them to explain them. Default: none
      # Locks:   <name>[, <name> ...] resources this round needs to itself (letters,
                                      digits, . _ - /, e.g. orders-table, tf/orders).
                                      Lanes sharing a lock never run at the same time,
                                      in either order, and a failure doesn't spread
                                      through a lock (unlike After:). Default: none
      # Step-Timeout: <2m, 30s, ...>  default limit for each step (--timeout overrides,
                                      --timeout 0 turns it off for one step). Default: none
      # Timeout: <30m, 1h30m, ...>    limit for the whole round. A step still running
                                      at the limit is stopped (FAIL, timeout) and the
                                      round ends. Default: none
      # Outputs: <name>[, <name> ...]  files or directories the round promises in $SWIM_OUT
                                      (.swim/out/<job>/<run>/, fresh each round), for the
                                      lanes that depend on it (input N name). A promised one
                                      missing at the end is FAIL; undeclared files are a WARN.
                                      They're hashed (a directory as a sorted manifest) into
                                      status, the END block and the chain, and made read-only.
                                      Not masked: never put secrets in outputs. Default: none
      # Matrix: KEY=a,b,c              run the round once per value (a cell); see MATRIX ROUNDS
      # Fail: soft|hard               hard: the first failed step ends the round (STOP
                                      hard failure) and goes to on_failure. Default: soft.
                                      Needs syntax 3
      # Handler-Timeout: <5m, ...>    the budget for all outcome handlers together, from
                                      when the round ends. Default: 5m
  Other keys in the header block (e.g. "# Ticket: OPS-42") are kept and shown
  in the log's round header. A value swim can't use (a bad Timeout) is
  recorded as WARN when the round starts, and the default applies.

  STAGES. Every job has the same four stages, in this order:
      snapshot   read-only capture of current state (snapshot steps)
      check      checks and gates; nothing changes yet
      change     the change itself; destructive steps behind guard flags
      verify     prove it worked (re-plan is a no-op, health checks)
  Start each with `stage NAME`. A stage a job doesn't need is simply left
  out (it shows as "none"). Steps before the first stage line are "setup".
  A stage out of order or declared twice, or `stage change` without a
  snapshot and a check stage before it, records a WARN line (the round
  continues). An unknown stage name stops the round. The log's END block and
  status.yml record each stage's result: PASS, FAIL, SKIP (only skipped) or none.

  OUTCOME HANDLERS (script syntax 3: `# swim: syntax 3`). A round may define
  bash functions swim calls when it ends, however it ends (the end of the
  script, summary, a gate, stop, a hard failure, a blocked command, Ctrl-C,
  a timeout, a bash error), like try / catch / finally:
      on_success() { run "tag migrated" aws ... ; }      # the round passed
      on_failure() {                                    # anything else
        reached change || return 0                      # nothing changed, nothing to undo
        if guard ORDERS_ALLOW_ROLLBACK "redeploy SST stack orders-prod"; then
          run "sst deploy" npx sst deploy --stage prod
        fi
      }
      on_exit() { run "remove temp bucket" aws s3 rb s3://orders-tmp --force ; }
  - Order: on_success or on_failure, then on_exit. Each has its own log
    section (-- handler on_failure). Their results never change the round's:
    a failed round stays FAIL, and the END block, status.yml, --yaml and the
    chain record each handler (handlers: on_failure PASS | on_exit PASS).
  - Handlers run soft: a failed step, a gate, stop or a declined confirm in
    a handler records the failure and the handler carries on, so every
    rollback step gets its attempt. A round whose on_failure failed exits 89
    ("failed, and the rollback failed"), not 1.
  - Context: SWIM_OUTCOME (pass, fail, stopped, interrupted, timeout),
    SWIM_STOP_REASON, SWIM_FAILED_STEP and SWIM_FAILED_STAGE (the first
    failed step).
  - Guards in handlers approve as anywhere else; an unapproved rollback is a
    dry run. After a Ctrl-C nobody is asked: approve rollbacks up front
    (queue --approve, a signed approval). swim plan lists each handler and
    the guards in it.
  - Ctrl-C: the first stops the round at a step boundary and runs its
    handlers (SWIM_OUTCOME=interrupted; return early if a rollback shouldn't
    follow an interrupt). Their steps start even though a stop was asked
    for. The second interrupts the running handler step and skips the rest;
    a third kills everything.
  - Handler-Timeout: (default 5m) is their budget together, from when the
    round ends, so a round that ran out its Timeout still gets time to roll
    back. Past it, the running step is stopped and the rest skipped.
  Lanes in other languages name commands instead: # On-Success:, # On-Failure:,
  # On-Exit: (or on-success:, ... in lane.N.yml), run with sh -c in a handler
  section with the same context and budget (see OTHER LANGUAGES).

  Rules for lane scripts:
  - Do not use `set -e`. Failed checks keep going; only gates stop the round.
  - run/gate/snapshot take argv, not a shell string. For pipes or redirects:
      run "count items" bash -c 'aws dynamodb scan --table-name T --select COUNT | jq .Count'
  - Load the pinned toolchain yourself (the template does it from config):
    non-interactive shells don't load nvm/asdf/pyenv.
  - Start every multi-step change with a read-only snapshot of current state.
  - Put every destructive step behind its own guard flag AND after a gate:
      gate "stack is ours (tag owner=swim-lane2)" bash -c '...exit 1 if not ours...'
      if guard FIN_ALLOW_DELETE_ZG_ITEMS "delete zg items table (2026-10-09: migrated to tf)"; then
        run "back up items" bash -c 'aws dynamodb scan ... > .swim/snapshots/zg-items.json'
        run "delete items table" aws dynamodb delete-table --table-name zg-items
      fi
    List each flag in the lane script header with the date and reason.
  - Make rounds rerunnable: gates must tell "ours" (tagged) from "theirs" so a
    rerun doesn't trip on resources the previous run created. Steps should be
    idempotent or detect their own prior success (VPNs drop).
  - End with a verification step (e.g. "re-plan is a no-op") and any shared audit.
  - Write the round's goal on the `# Round:` line: `swim run`, `swim status`
    and the live view show it. A lane script without a Round: line is not run.

  Example:
      #!/usr/bin/env bash
      # swim: syntax 2
      # Round:   Cut over orders-api from SST to Terraform
      # Job:     3f2a9c1e-7b4d-4e2a-9c1e-7b4d4e2a9c1e
      # After:   1
      # Owner:   zach
      # Created: 2026-10-09
      # Guards:  ORDERS_ALLOW_SST_REMOVE  remove SST stack orders-prod (2026-10-09: tf owns it)
      # Timeout: 30m
      _swim_lib=$("${SWIM_BIN:-swim}" lib) || exit 1; eval "$_swim_lib"
      lane_init 2
      . "$HOME/.nvm/nvm.sh" && nvm use >/dev/null || stop "toolchain failed"

      stage snapshot
      snapshot "cfn template" aws cloudformation get-template --stack-name orders-prod
      stage check
      run  "tf plan" terraform -chdir=infra/orders plan -detailed-exitcode
      gate "tf state has orders table" bash -c 'terraform -chdir=infra/orders state list | grep -q aws_dynamodb_table.orders'
      gate "DeletionPolicy is Retain (deployed)" bash -c 'aws cloudformation get-template --stack-name orders-prod | grep -q Retain'
      stage change
      if guard ORDERS_ALLOW_SST_REMOVE "remove SST stack orders-prod (2026-10-09: tf owns it)"; then
        run "sst remove" npx sst remove --stage prod
      fi
      stage verify
      run "verify: re-plan is a no-op" terraform -chdir=infra/orders plan -detailed-exitcode
      summary

MATRIX ROUNDS
  One lane script runs once per value, each run a cell with its own log,
  status, job and result:
      # Round:  Cut over $SVC from SST to Terraform
      # Matrix: SVC=orders,billing,users     (or SVC=@services.txt: one per line)
      # Matrix-Parallel: 2                   cells at once (default 1), each in a
                                             slot of the run's --parallel
      # Matrix-Fail: stop                    skip cells not started after a failure
                                             (default continue: every cell runs)
      # Locks:  tf/$SVC                      $KEY in Round, Locks and Outputs is
                                             each cell's value
  - Several Matrix: lines give the cross product (cells named
    ENV=prod,SVC=orders); # Matrix-Exclude: ENV=prod,SVC=search drops
    combinations. At most 256 cells.
  - A cell's process gets each key as an env var ($SVC) and SWIM_CELL. Its log
    is .swim/logs/agentN.<cell>.log; its job <job>/<cell>; status.yml lists
    it under its lane's cells:.
  - The lane passes only if every cell does. After: 3 waits for the whole
    lane; After: 3[orders] needs only that cell to pass.
  - Rerun: swim run 3 --failed runs only the cells that didn't pass; swim run
    '3[billing]' (or <job>/billing) runs one cell.
  - Read: swim log 3 lists the cells; swim log '3[orders]' shows one.
  - The value file (@services.txt) is part of the script's hash: approvals,
    queue pins and the chain cover the list. Each cell asks its own guard
    questions, naming its cell.

OTHER LANGUAGES
  A lane script can be any runnable: lane.N.py, lane.N.js, lane.N.ts, lane.N.rb,
  a compiled program lane.N, a plain bash script. Exactly one per lane (two
  is an error). `swim new N "<goal>" --lang py|js|ts` writes a template.
  How it runs (decided before the lane starts):
    1. lane.N.sh: bash, as always.
    2. A #! line: that command (no question asked).
    3. runners: for its extension: the operator's (config.yml, this repo's
       section) wins over the repo's committed swim.yml.
    4. A compiled or executable file with no runner: run as itself.
    5. Otherwise, at a terminal, swim looks the extension's runners up on
       PATH (.js node, bun, deno; .ts tsx, ts-node, bun, deno; .py python3,
       python; .rb ruby; ...), asks "Run .ts lanes with /usr/local/bin/tsx?
       [Y/n, a number, or type a command]" and saves the answer as
       runners.ts for this repo. Off a terminal (CI, swim watch) the lane
       fails at start with the exact fix: a #! line, `swim config
       runners.ts tsx`, or swim.yml (runners: {ts: tsx}) for everyone.
  A script that doesn't load the bash library (no lane_init) runs inside
  swim's wrapper, which opens and closes its round, exports SWIM_LANE,
  SWIM_JOB, SWIM_RUN, STEP_LOG and the rest, and puts the git shim first on
  PATH. Steps are swim commands (they read SWIM_LANE):
    swim run [options] "<label>" -- cmd [args...]     a step (PASS/FAIL)
    swim gate [options] "<label>" -- cmd [args...]    a step that ends the round on failure
    swim snapshot [options] "<label>" -- cmd ...      a step whose output is saved
    swim guard FLAG "<action - date, reason>"         exit 0 if approved, 1 if not (dry run)
    swim stage snapshot|check|change|verify
    swim drift "<what differs>"    swim stop "<reason>"
    swim msg [--progress N/M] "<text>"                a status message (live view, status, hub)
    swim input N|JOB NAME    swim output KEY VALUE    outputs between lanes (Outputs:)
  (options as for run in a bash lane: --timeout, --retry, --backoff,
  --retry-on, --no-retry-timeout, --soft). Outcome handlers are commands:
      # On-Failure: python3 rollback.py           (on-failure: in lane.N.yml)
      # On-Exit:    swim run "remove tmp" -- rm -rf /tmp/orders
  run with sh -c when the round ends; in them swim gate and swim stop record a
  failure and end nothing. # Fail: hard makes a failed swim run end the round
  (swim run --soft opts out). Both need `# swim: syntax 3` in the header; a
  sidecar with these keys needs none. A failed gate, swim stop, a refused git
  push or the operator's stop ends the program even if it ignores the exit
  code (SIGTERM to its process group, SIGKILL after 5s). A program that
  never calls swim run is logged as one step: its whole output (masked),
  passed or failed by its exit code. In Python:
      import os, subprocess
      def swim(*a): return subprocess.run([os.environ.get("SWIM_BIN", "swim"), *a]).returncode
      swim("stage", "check")
      swim("gate", "target is ours", "--", "aws", "s3api", "head-bucket", "--bucket", "orders")
      if swim("guard", "ORDERS_ALLOW_DELETE", "delete bucket orders (2026-10-13: replaced)") == 0:
          swim("run", "delete bucket", "--", "aws", "s3", "rb", "s3://orders")
  Native SDKs: instead of a process per step, a lane can use swim's SDK
  for its language, over a socket swim's wrapper serves for the lane
  (protocol swim.lane/v1, proto/swim/lane/v1/README.md). swim still decides
  everything; the SDK raises RoundEnded when the round is over, and the
  program has 10s to unwind (finally blocks) before it is stopped.
      Python      sdk/python (pip install swim-lanes; import swim)
                    with swim.round() as r:
                        r.gate("tf plan", ["terraform", "plan"])
                        with r.step("table is empty", gate=True) as s:   # in-process
                            s.log("items: 0"); s.require(n == 0, "has items")
      TypeScript  sdk/ts (@gates-brightly/swim; Node, Bun, Deno)
                    await round(async (r) => { await r.gate("tf plan", ["terraform", "plan"]); });
      Go          sdk/go/swim (compiled lanes): os.Exit(swim.Round(func(r *swim.R) error { ... }))
  Each has run, gate, snapshot, evidence, step (in-process, logged as
  "PASS  <label> (in-process)"), stage, guard, confirm, drift, stop, msg,
  input, output, and outcome handlers (on_success / on_failure / on_exit,
  registered first). Register # Includes: lib/*.py for the local modules a
  lane imports: they're hashed with the script, so approvals cover them
  (lint warns about local imports it doesn't cover).
  Header keys are comments, # or //, as in a bash lane. A binary (or any
  lane) can keep them in a sidecar lane.N.yml instead; its keys win:
      round: cut over orders
      job: 3f2a9c1e-...
      after: [1, 2]
      guards:
        ORDERS_ALLOW_DELETE: delete bucket orders (2026-10-13: replaced)
      locks: [orders-db]
      timeout: 30m
      step-timeout: 5m
  Approvals, the queue's pins and the chain of custody hash the script file
  itself (the binary, for a compiled lane). Env files apply to every lane;
  the deprecated .lane.N.rc only to bash lanes.

LINT
  `swim lint` reads lane scripts and reports problems as error, warn or info
  with file:line, a fix and a [code]. It exits 1 on any error (--strict: on
  warnings too). `swim run` refuses to start (exit 2) on the lint errors it
  wouldn't otherwise catch: `set -e` and a missing or wrong `lane_init N`.
  To accept a finding, say why, in a disable comment (the reason is required):
      rm -rf "$TMP"   # swim:lint-ignore destructive scratch dir this round made
      # swim:lint-ignore bash4 runs only on the Linux CI box      (next line)
      # swim:lint-ignore-file cross-lane reads lane 1's output from yesterday's run
  `swim doctor` checks the environment the same way; it never changes config,
  lane scripts or git. `swim doctor --fix` only rewrites swim's .gitignore
  block, removes stale .swim/laneN.pid files and moves plain .lane.N.rc files
  into .env.swim.

ENV FILES
  Lanes get non-secret context (STAGE, AWS_PROFILE, table names) from
  declarative KEY=VALUE files. swim parses them; it never runs them as shell.
      # ~/.config/swim/env.swim   general keys, then [repo PATH] sections
      STAGE=dev
      AWS_REGION=us-east-1
      [repo ~/dev/orders]
      AWS_PROFILE=orders-prod

      # <repo>/.env.swim          [lane N] sections only (git-ignored)
      [lane 2]
      TABLE=orders-v2

      # <repo>/swim.yml           shared defaults, committed (CI gets them)
      env:
        LOG_LEVEL: info
  - Precedence, highest first: the shell (what you type wins), then the
    lane's section, the repo's section, swim.yml env:, the general keys.
  - Format: KEY=VALUE, # comments, '...' or "..." around a value. No export,
    no $VAR or $(...): a line that doesn't parse stops the run before any
    lane starts, naming the file and line ('$x' means the characters).
  - No guard flags. A key that is a guard of a selected lane, or matches a
    guards: glob in lookup.yml (FIN_ALLOW_*), stops the run. Approvals come
    only from the shell, the prompt, -y, signatures or a queued batch.
  - Masked: every value from a file (6 characters or more) is masked in
    logs, snapshots, status and output, whatever its name. Still, never
    store secrets there: store AWS_PROFILE, not the key.
  - Recorded: the round header lists the files that applied (env-files:),
    status.yml and the chain record their hash (env_sha256: same script and
    same env hash, same inputs), and a queued lane whose env changed since it
    was queued is skipped. `swim env N` shows what a lane gets.
  - Lanes started by swim run (any language) get them; a bash lane run
    directly with bash doesn't (its round still records the hash).
  - .lane.N.rc is deprecated: lane_init still sources it, with a WARN, but a
    guard flag it sets no longer approves (guard asks as if it were unset).
    `swim doctor --fix` moves a plain one into .env.swim.

SYNTAX
  Lane scripts and lane logs say which syntax they use ("# swim: syntax 2" near
  a script's top, "# swim lane log | syntax 2" as a log's first line; none
  means syntax 1). This swim writes syntax 2, reads lane logs in syntax 1
  and 2, and lane scripts in syntax 1 to 3.
  - Older files are migrated automatically when any swim command loads the
    repo: rewritten in place, originals copied to .swim/migrations/<time>/,
    the migration recorded in .swim.log. A running lane's files wait until
    it finishes. Syntax 1 scripts get the syntax line, a Created: date, and
    stage lines where the old template's numbered sections were.
  - A file in a newer syntax stops swim with an update prompt
    (go install github.com/gates-brightly/swimlane/cmd/swim@latest).
  Syntaxes:
    3   (lane scripts only) outcome handlers (on_success, on_failure, on_exit,
        or On-*: commands) and Fail:. Declare it only when you use them; a
        syntax 2 script is never rewritten to 3, and logs stay syntax 2.
    2   header metadata (Owner, Created, Guards, Timeout, ...), the four
        stages, and logs grouped by round and stage with output fenced by "| "
    1   no syntax line, no stages, === STEP / --- output log framing

SAFETY RULES
  - Secrets are masked, as a backstop. swim replaces the values of secret
    variables (config secret_env, plus names like *_TOKEN, *_SECRET,
    *_PASSWORD, *_API_KEY with secret_env_auto) and well-known credential
    shapes (AWS key ids, GitHub/Slack tokens, JWTs) with *** in step output,
    commands, snapshots, the terminal stream, labels, status.yml and
    .swim.log, including their base64 and URL-encoded forms. A secret in
    header_env is logged as NAME=***(len N), and each round header says
    "masked: N vars (NAMES)". Masking does NOT cover output a step pipes or
    writes elsewhere, or values split or transformed. The rule stands: never
    print secrets; print keys or lengths only.
  - Secrets from swim secret (bash: $(swim secret get NAME); the SDKs:
    secret.get("NAME")) are masked exactly, by name: ***(db_password).
    A swim run decrypts them once at start (asking the key's passphrase, if
    any, before the live view) and every process in every lane masks all of
    the repo's secrets, whichever it uses. .swim.log records which lane got
    which secret and how, never a value. They guard against leaks into logs,
    the hub and git, not against lane code: a lane runs as you and could
    read your key itself.
  - swim never pushes, commits or pulls, and neither do lanes. A lane script
    containing `git push`, `git commit` or `git pull` (or a repo's
    blocked_commands) fails before it starts; a step whose command contains one
    at runtime is refused (BLOCKED, exit 87) and the round stops, even for a
    plain `run`; and a git shim first on each lane's PATH refuses those
    subcommands however git is called (git -C dir push, scripts the lane runs).
    Committing is the operator's decision, made outside swim. The match is on
    text, so even `echo "git push"` is refused: rephrase it.
  - Snapshot before any change. Back up stateful data (e.g. table items)
    before removal, and know how you would restore it.
  - Read the DEPLOYED state (e.g. the CloudFormation template's
    DeletionPolicy); never assume it from code.
  - One guard flag per destructive or irreversible action, recorded in the
    lane script header with date and reason. Never default a flag on.
  - Prefer reversible operations (disable, unsubscribe, keep a saved copy)
    over deletes when ownership is unclear.
  - Probes must not cause side effects: no messages, emails, payments or
    mutations. Use inputs rejected by validation, health routes, dry runs.
  - Gates are fail-closed: an empty or unknown answer stops the round.
  - Logs never contain secret values. Print keys or lengths only
    (e.g. `bash -c 'echo ${#API_KEY}'`). Never list a secret in header_env.
  - Rounds must be safe to rerun.
  - Approval, signing and the chain prove who decided what; they don't make
    a script safe. A guard is advisory (a bash function in the lane), and an
    approved script runs with the operator's access. What swim protects
    against, and what it doesn't: docs/trust-model.md
    (https://github.com/gates-brightly/swimlane/blob/main/docs/trust-model.md).
  - When something goes wrong (an orphaned queue entry, a lane stuck
    running, swim verify failing, a lost signing key, a lock mismatch), see
    docs/recovery.md in the same repo. Never edit .swim/chain.jsonl.

READING RESULTS
  Lane log (.swim/logs/agentN.log): append-only plain text, written to be
  read with cat or an editor; `swim log N` renders it (colour, folded output,
  relative times; --full, --raw). Every line says what it is by how it starts:
      # swim lane log | syntax 2 | swim N           first line: the log's syntax
      == ROUND <utc>  job=<id>  <Round>             a round starts
         run: <run id> | script: lane.N.sh | owner: ... | after: ... | timeout: ... | guards: ...
         | git: <branch>@<sha> | runtime: ... | env: STAGE=... ...
      -- stage <name>  <hh:mm:ss>                   a stage starts
        PASS  <label>                <dur>s  <hh:mm:ss>    a step (2 spaces, kind, 2 spaces)
        FAIL  <label> (exit <code>)  <dur>s  <hh:mm:ss>    ... or (exit 130, interrupted),
                                                           (timeout: Timeout 30m reached),
                                                           (timeout: step limit 2m),
                                                           (exit 1, attempt 4/4)
              $ <command, shell-quoted so it can be re-run>
              -- attempt 1/4                       with --retry: each attempt, its
              -- exit 255 (3.0s); retry in 5s      outcome and the wait before the next
              | <command output, ANSI stripped>    output is always fenced with "| "
              saved: <snapshot path>
        BLOCKED  <label> (matched "git push"; swim never writes to git)
                                                    a refused command (exit 87); counts as FAIL
        SKIP  <label> (dry run: set FLAG=1 to approve)
        SKIP  <label> (dry run: declined at the prompt by <user>; set FLAG=1 to approve)
        APPROVED  <label> (FLAG=1)
        APPROVED  <label> (approved at the prompt by <user>)
        DRIFT  <what>
        STOP  <reason>
        WARN  <what>                                stage order, bad header values
        CHECKED  stopped before stage change         a read-only check (swim plan --check) ended
                                                    where change begins; in agentN.check.log
        MSG  <text> (7/25, <hh:mm:ss>)              a status message (msg); never a result.
                                                    One posted during a step is in its
                                                    block: -- MSG  <text> (...)
      -- handler on_failure  <hh:mm:ss>             an outcome handler's section: its
                                                    results never count toward the round's
      == END <PASS|FAIL|INTERRUPTED>  pass=P fail=F skip=S drift=D  exit=E  <dur>s  <utc>  run=<run id>
         stages: snapshot PASS | check PASS | change SKIP | verify PASS
         handlers: on_failure PASS | on_exit PASS     (if any ran)
         outputs: stats.json 2.1 KB 3f2a9c1e0b7d | pages 14 files, 1.2 MB 9d8e...  (if any)
         failed: FAIL  <label> (exit <code>); ...
  Results are the lines starting "  KIND  " (grep -E '^  (FAIL|BLOCKED)' finds
  every failure); anything indented 8 spaces belongs to the step above it and is
  never a result. The current round is everything after the last "== ROUND".
  A running step's block isn't in the file until it ends; swim log adds it
  (RUNNING  <label> (in progress), with its output so far), swim log N
  --yaml includes it as a RUNNING result, and swim log N -f streams it.
  To wait for a job from a script: swim log <job> --until-done (exits with
  the round's status).

  .swim.log (project log, oldest first; one line per event):
      <utc>  <user>  <event>  [swim N]  [job=<id>]  [run=<run id>]  <detail>
  events:
      init         swim init ran (detail: lanes=N)
      new          a round was written (detail: the round goal)
      run          swim run started (detail: swim 1,2,4)
      start        a lane began its round (also when run directly with bash)
      pass / fail / interrupted
                   a round ended (detail: counts, exit, duration, goal, and
                   after "|" the failed steps)
      skip         a lane was skipped (detail: why, e.g. "swim 1 failed")
      approve      the operator approved a guarded step at the prompt
                   (detail: the action, the flag and who)
      decline      ... declined it, or no answer came (detail: the action, why)
      run-done     swim run finished (detail: passed/failed/skipped counts)
      archive      a log was archived (detail: archive file name)
      stub         a lane was stubbed (job= is the job it replaced)
      note         swim note (detail: the text)
  Its details are summaries; the evidence is in the lane log (swim log N).

  .swim/status.yml (also `swim status`, `swim status --yaml`):
      updated_at: <utc>
      root: <repo root>
      branch: <branch>@<sha>
      lanes:
        - lane: 1
          state: running   # idle|waiting|locked|queued|running|passed|failed|skipped|interrupted
          pending: <Round: line of lane.N.sh on disk, "" if stub/none>
          pending_job: <Job: id of lane.N.sh on disk>
          round: <round of the last or current run>
          job: <job id of the last or current run>
          run: <swim run id of that round>
          script: lane.1.sh
          log: .swim/logs/agent1.log
          waiting_on: []   # e.g. [2] while waiting on swim 2
          reason: <why skipped, or what a waiting lane waits for>
          locks: [<locks the running round holds>]
          pid: <script pid while running>
          started_at / finished_at: <utc or null>
          duration_s: <seconds or null>
          exit_code: <int or null>
          pass / fail / skip / drift: <counts for the round>
          current_step: <label of the step in progress or last run>
          failed_steps: [<FAIL lines>]
          last_archive: <last archived log name>
  `swim status` shows "running?" when a lane's pid is gone (killed terminal);
  treat that lane's round as interrupted.

  YAML for scripts and agents. Prefer these to scraping text: the text layouts
  are for people and may change, the schemas are versioned. Each document
  carries "schema:"; fields may be added within a version, and removing or
  renaming one bumps it.
    swim run|all --yaml       swim.run/v1: one document per event, "---"
                              between them, flushed as they happen; no panel,

        event: run      run, lanes: [..], max_parallel, at

        event: step     lane, label, stage, result (PASS|FAIL|BLOCKED|SKIP|

                        a lane's steps come together just before its finish
        event: msg      lane, message, progress: a running round's status message

        event: finish   lane, job, result (passed|failed|skipped|interrupted),

          ts: tsx                        # swim asks the first time, and saves the answer per repo

  A repo may commit swim.yml at its root: the same keys as a repos entry
  (deps, max_parallel, blocked_commands, secret_env, header_env, ...).
  It applies on top of defaults and under the operator's repos entry, so CI
  runners (no config of their own) and every operator share it. Unknown keys
  are an error. `swim config` shows it as repo_file.
  A lane's dependencies are config `deps` plus its script's `# After:` line.
  Dependencies in the same `swim run` are waited for. A dependency outside
  the run must already be satisfied, otherwise the lane is skipped:
    - by lane number: if that lane holds a pending round, the round must have
      passed (a stubbed or empty lane never blocks);
    - by job id: that job must be the lane's last run, and have passed.
  Unresolvable `# After:` references and cycles stop `swim run` before
  anything starts, and so does an After: lane with no script, log or past
  run (a typo). Lanes are 1..99.

  Chime (operator preference; workers never set it): after `swim run` /
  `swim all` prints its summary, swim rings the bell (twice on failure) if
  chime is true, or failure and the run didn't fully pass, the run took at
  least chime_min_s, stdout is a terminal (not needed for notify) and CI
  isn't true. sound adds a system sound, notify a desktop notification.
  --chime / --no-chime override it for one run. Set it with
  `swim config chime true|false|failure` (--repo for this repo only).

INTERRUPTING
  Lanes run in their own process groups, so Ctrl-C reaches only swim, which
  decides what the lanes get:
    1st Ctrl-C  stop gracefully: each running lane finishes its current step
                (nothing is sent to it), starts no other, and ends
                interrupted (exit 130) with
                "STOP  interrupted by operator (after: <step>)"; a step
                waiting to retry stops waiting; a waiting confirm is
                cancelled; lanes not yet started are skipped. The panel
                shows "stopping <step>".
    2nd Ctrl-C  force quit: SIGINT to every running lane's process group
                (tools that clean up on SIGINT, like terraform, get exactly
                one), then SIGKILL after interrupt_grace (5s).
    3rd Ctrl-C  SIGKILL now.
  The time between presses doesn't matter. SIGTERM (a CI cancel) stops
  gracefully and forces after term_grace (10s); SIGHUP (terminal closed)
  forces at once. interrupt: immediate (or --interrupt immediate) makes the
  first press force. `swim interrupt N` stops one lane gracefully from
  another terminal. A single lane given the terminal (so confirm can read
  it) stays in swim's process group and gets Ctrl-C directly, at once.
  A step runs in a process group of its own (see TIME LIMITS): swim step
  passes the force quit's SIGINT on to it, and the kill reaches it through
  .swim/logs/<log>.partial.pgid, where swim step records it while it runs.
  Mechanism, for lane authors: a stop request is .swim/laneN.stop (holding
  the run id) plus SIGUSR2 to the lane's bash; swim step refuses to start
  while it exists (exit 86) and the library records the STOP. A lane run
  directly with bash has no launcher: Ctrl-C interrupts it at once.

CHAIN OF CUSTODY
  Every approval and every round is recorded in .swim/chain.jsonl, one
  signed entry per line, each carrying the SHA-256 of the line before it
  (like commits: the sequence is the attestation):
    approve  lane, job, the script's hash, the guard and its action, who
             approved (name, key) and how: signature (approvals of this
             script), standing (a standing approval of the queuer's jobs),
             prompt, flag (FLAG=1), auto (-y) or queue; signed approvals
             carry their approvers' own signed events
    round    the script's hash, the hash of the round's log section, the
             result and exit, and the approvals it used
    grant / revoke   approvals given or withdrawn on this machine
    repair   swim chain repair removed a half-written final line: its size,
             its SHA-256 and the .swim/chain.tail-<time>.bak that keeps it
  The runner signs each entry with its SSH key (config signing_key; default
  ~/.ssh/id_ed25519; signing: auto | required | off). The scripts that ran
  are kept by hash under .swim/scripts/. Changing a log, a kept script or
  any entry (or removing or reordering entries) is provable: swim verify.
  swim history shows the chain by approver. Entries have no size limit, and
  each is synced to disk as it is written. A write cut short (a crash or a
  full disk) leaves a last line with no newline; swim then refuses to
  append until swim chain repair removes it.
  Approving: swim approve N --guards FLAG approves lane N's exact script;
  co-approvers run the same; swim approve --auto USER approves every job
  USER queues (swim queue add signs the batch with the queuer's key, so
  who queued it is proven, not claimed), until swim revoke --auto USER.
  The approvals live in committed files under approvals/, each an ordered,
  signed log of approve and revoke events. A guard approves when the
  approvers of its script plus the standing approvals of its batch's
  queuer, named by lookup.yml, meet lookup.yml's rule for it; swim watch
  --approved runs fully approved scripts by itself. A script edited after
  approval no longer matches, so the approval stops counting.
  lookup.yml (repo root) names keys and groups them: see swim keys --help.
  Signing uses ssh-keygen -Y (OpenSSH 8.0+); anyone can check a signature
  with it. Signing never prompts: a key with a passphrase needs ssh-agent
  (give the .pub path as signing_key).
